# ЛР 2 — обоснование актуальности ВКР

**Тема ВКР:** Разработка программной системы компенсации дрейфа ориентации при захвате движений с использованием оптических измерений.

**Автор или участники команды:** Макаров Максим Вячеславович. Работа выполняется индивидуально.

**Вклад каждого участника при командной работе:** Автор самостоятельно выполняет обзор, проектирование, разработку и экспериментальную оценку.

### Выводы по обзору

Рассмотренные работы подтверждают применимость объединения инерциальных и оптических измерений. Для реализации целесообразно использовать кватернионное представление вращения, калибровку камеры, геометрическое определение позы маркера и коррекцию с учётом качества наблюдений [3, 4, 6, 11, 14]. Обучение модели полного тела не является необходимым условием проверки отдельного корректора.

Основной исследовательский вопрос формулируется следующим образом: уменьшает ли изменение доверия к оптическому наблюдению ошибку ориентации по сравнению с коррекцией с постоянным коэффициентом при задержках, выбросах и временном перекрытии ориентира? Ответ должен быть получен экспериментально. Общий принцип объединения камеры и IMU уже представлен в литературе [8, 9].

Работы по моделированию и доступные записи позволяют организовать разработку без покупки датчиков [1, 7, 8]. При этом синтетические испытания устанавливают свойства алгоритма в выбранной модели ошибок. Проверка на реальных устройствах нужна для отдельного вывода о переносимости результата на SlimeVR.

## 3. Обзор и сравнение аналогов

### Прямые аналоги

**SlimeVR Server и Stay Aligned [12, 13].** Это ближайший практический аналог по обработке инерциального захвата и коррекции дрейфа. В рассмотренном описании Stay Aligned использует настроенные позы пользователя. ВКР предполагает исследование коррекции по оптическому наблюдению; преимущество над штатной обработкой заранее не утверждается.

**HybridCap [9].** Функциональный аналог по объединению одного видеопотока и инерциальных измерений. Он решает более широкую задачу восстановления движений. Проектируемая программа выделяет коррекцию ориентаций в отдельный модуль и предусматривает проверку на входных записях с управляемыми ошибками.

### Косвенные аналоги

**Physical Inertial Poser [10].** Использует физическую оптимизацию движений по инерциальным данным. Полезен как пример ограничения неестественных поз, но не предоставляет оптического ориентира для исследуемой коррекции.

**Определение позы по маркерам ArUco средствами OpenCV [11, 14].** Решает оптическую часть задачи и может быть использовано как компонент. Само по себе обнаружение маркера не объединяет измерения с инерциальным потоком.

### Таблица сравнения

**Почему выбраны эти критерии:** Сравнение проводится по входным данным, источнику внешней коррекции, основной функции и способу проверки без новых носимых устройств. Эти критерии отражают требования к программе и доступность экспериментального стенда. Численное ранжирование точности не выполняется: результаты разных публикаций получены на разных данных и несопоставимых конфигурациях.

### Выводы по сравнению

Из существующих решений предполагается использовать способы представления движений и открытые интерфейсы обмена, а из OpenCV — получение оптических наблюдений. Собственная разработка будет включать оценку доверия к наблюдению, применение поправки и воспроизводимый стенд проверки.

Отличие проекта состоит в явно заданных сценариях дрейфа и потери наблюдений, единых метриках и возможности повторить эксперимент без физического комплекта трекеров. Это ограниченный результат программной разработки. Превосходство по точности и пригодность для конкретного оборудования должны проверяться отдельно.

## 4. Итоги

**Итоговая тема ВКР:** Разработка программной системы компенсации дрейфа ориентации при захвате движений с использованием оптических измерений.

**УДК для тезиса:** 004.94:004.932. Рабочий индекс объединяет компьютерное моделирование и обработку изображений; перед подачей тезисов уточняется по правилам выбранного издания.

**Ключевые слова:** захват движений, инерциальные измерения, дрейф ориентации, оптическая коррекция, кватернионы, компьютерное зрение, имитационное моделирование, виртуальный персонаж.

### Актуальность исследования

Для анимации виртуального персонажа важны устойчивые ориентации сегментов тела. Накопленная ошибка меняет восстановленную позу, а резкая коррекция может приводить к заметным скачкам. Практическая значимость проблемы подтверждается описанием дрейфа и способов его исправления разработчиками SlimeVR [13].

Научные публикации показывают два дополняющих направления: восстановление движения по разреженным инерциальным данным и объединение таких данных с изображением [7–10]. Отечественные работы рассматривают моделирование погрешностей датчиков и их оптическую проверку [1, 2]. Следовательно, разработка воспроизводимого способа оценки коррекции связана с реально исследуемой технической задачей.

Оптический источник полезен только при достаточном качестве наблюдения. Перекрытие, ошибка калибровки или рассогласование времени способны ухудшить результат. Поэтому исследование сосредоточено на доверии к внешней коррекции и восстановлении после её временного отсутствия. Практический результат предназначен для разработчиков приложений захвата движений и анимации персонажей.

### Цель исследования

Разработать программную систему коррекции дрейфа ориентации и на воспроизводимых данных оценить, как учёт достоверности оптических наблюдений влияет на угловую ошибку, устойчивость и задержку по сравнению с коррекцией с постоянным коэффициентом.

### Задачи исследования

1. Определить требования к входным данным, единый формат ориентаций, временных меток и признаков качества.
2. Разработать средства генерации эталонных траекторий и внесения заданных ошибок ориентации, оптических выбросов и пропусков.
3. Реализовать согласование систем координат и времени; подготовить оптическую оценку по маркеру либо воспроизведение таких оценок из записи.
4. Реализовать базовую коррекцию с постоянным коэффициентом и исследуемый вариант с оценкой доверия и ограничением скорости изменения поправки.
5. Подготовить визуализацию исходных и исправленных данных в Unreal Engine и сохранение результатов обработки.
6. Провести серию сопоставимых экспериментов, включая потерю видимости и восстановление наблюдения.
7. Оценить угловую ошибку, восстановление после пропусков и время обработки; определить условия, в которых коррекция помогает или ухудшает результат.

### Датасеты и сервисы

**Собственный генератор траекторий — обязательная основа стенда.** Планируется генерировать остановки, плавные повороты и составные вращения с известной эталонной ориентацией. На их основе формируются отдельные входные потоки с постоянным и изменяющимся дрейфом, шумом и ошибками времени. Для воспроизводимости сохраняются параметры генерации и начальное состояние генератора случайных чисел.

На первом уровне моделируются уже рассчитанные ориентации. На втором предусматривается синтетическая видеопоследовательность маркера с известной геометрией и параметрами камеры. Это позволяет проверить оптический модуль без носимых датчиков и без доступа к внешнему набору. Такая модель не воспроизводит все физические свойства реального IMU.

**TotalCapture — дополнительный исследовательский набор [8, 16].** Содержит синхронные видео, инерциальные измерения и разметку Vicon. Перед использованием нужны получение доступа, соблюдение условий и сопоставление систем координат. В наборе не предполагается наличие требуемых проекту ArUco-маркеров. Данные полезны для проверки импорта и движения сегментов; применение к оценке углов требует отдельного согласования ориентаций и креплений. Доступность полного набора не является условием завершения работы.

**DIP-IMU — дополнительный источник записанных инерциальных движений [7, 17].** Его можно использовать для проверки обработки временных последовательностей после получения данных по лицензии. Наличие независимого синхронного оптического эталона для требуемого эксперимента не предполагается. Набор не рассматривается как готовая замена TotalCapture.

**Собственные записи Quest 3 — практическая апробация без SlimeVR [15].** Можно записывать позы контроллера через OpenXR, прикрепить к нему жёсткий маркер и сравнить согласованные во времени потоки. Дрейф во входной ориентации вносится программно. Это проверяет цепочку обработки и оптическую коррекцию, но не является измерением реального дрейфа SlimeVR. Погрешность готового трекинга Quest также должна учитываться.

**SlimeVR — дополнительный источник при наличии устройств [12].** После получения комплекта планируется реализовать адаптер доступных данных и испытать программу на реальных движениях. Этот этап расширяет проверку, но не входит в обязательные условия получения основного результата.

Для обязательного сценария внешние облачные сервисы и платные API не требуются. Собственные записи, генератор, настройки экспериментов и код могут храниться в репозитории. Лицензируемые сторонние наборы в него не включаются.

Сравниваются три режима на одинаковых входных последовательностях: обработка без коррекции; комплементарная коррекция с постоянным коэффициентом; исследуемая коррекция с изменяемым доверием и плавным восстановлением. Параметры настраиваются на отдельном наборе сценариев и фиксируются до контрольных испытаний.

Предусматриваются следующие условия: медленно нарастающая ошибка курса; изменение скорости её накопления; шумные оптические измерения; кратковременные и длительные пропуски; единичные ложные наблюдения; задержка видеопотока. Для каждого условия выполняются повторения с разными начальными состояниями генератора. Отдельно проверяются вычислительные затраты при обработке одного, шести и десяти потоков ориентации.

Качество планируется оценивать по средней угловой ошибке, RMSE и 95-му процентилю, остаточному уходу курса, времени восстановления после пропусков, резкости применяемой поправки и времени обработки. Порог восстановления и параметры контрольных сценариев фиксируются до сравнения алгоритмов. Время вычисления в воспроизведении не приравнивается к полной задержке системы с камерой и беспроводными устройствами.

Без физических трекеров результаты будут относиться к моделям ошибок и используемым записям. Эталонная ориентация задаётся отдельно и доступна только модулю оценки. Проверка на реальных устройствах нужна для отдельного вывода о переносимости результата на SlimeVR. На этапе обоснования численные результаты эффективности ещё не получены.
